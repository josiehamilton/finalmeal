## 1. What we're building

Final Meal is a social food app for iOS, Android and the web. Each person picks the **five dishes** they'd choose for their final meal (the "Final Meal") plus unlimited **Honorable Mentions**. People follow each other, discover dishes on a map, and share **live lists** (by city, food type, tag, everything, or their five) through links that open on the web or in the app.

**MVP success:** the app runs end to end locally in Docker, then in the cloud, with TestFlight and Android internal-testing builds that real testers can use for every MVP flow below.

### 1.1 MVP scope

- Sign-up and login: email code, Apple or Google; profile (name, @username, photo, bio, home city); Public or Private setting (default Public)
- Add a dish on one screen: restaurant search with custom fallback, smart dish suggestions, Final Meal or Honorable, optional photo, optional note, optional tags (expand inline)
- Final Meal (5 slots) + Honorable Mentions; swap flow ("dethroned"); promote Honorable to Final Meal
- Feed (Following + Nearby), pick detail, save to try
- Discover: map, search (dishes, spots, people, shared lists), filters (pick type, distance, food type, dietary)
- Follow, followers/following, activity (in app) + push notifications
- Sharing: share screen, Your lists, live links, web list and map pages with sign-up prompts, link previews, links that open the app when installed
- Settings: edit profile, notifications, privacy & safety (Public/Private, blocked accounts, download data, delete account), report

### 1.2 Not in the MVP (designed, built after)

Feed ads + paid ad removal (pricing decided after the cost model), story-image sharing, advanced fraud detection, admin dashboard (merges, moderation), a full web app beyond the shared-list pages and sign-up.

## 3. Architecture

```
 iPhone/Android ─▶ Expo app (apps/mobile) ─┐
                                            ├─▶ Supabase
 Browser (shared link) ─▶ Next.js (apps/web)┘     Postgres + PostGIS + pg_trgm
                                                  Auth (email OTP, Apple, Google)
 Both ─▶ MapLibre ─▶ map tiles                    Storage (photos, image resizing)
                                                  Realtime (activity)
                                                  Edge Functions (attestation, push,
                                                  link previews, trust jobs)
                                                        ▲
                         Foursquare Open Places ────────┘ monthly import job
```

### 3.1 Repository layout (`~/Documents/FinalMeal`, remote `github.com/josiehamilton/finalmeal`)

| Path | Purpose |
|---|---|
| `apps/mobile` | Expo app (Expo Router), iOS + Android |
| `apps/web` | Next.js: `/l/[slug]` shared-list pages (list + map), sign-up, `/.well-known/` link files for the app, link-preview images |
| `packages/core` | Shared rules and types: slot limits, tag lists, dish-name normalisation, restaurant grouping, list-filter evaluation types |
| `packages/api` | Typed client used by both apps: every read and write goes through it |
| `packages/ui-tokens` | Colours, type scale, spacing, radii, fonts from the canvas |
| `supabase/` | Migrations, row-level-security policies, SQL functions, Edge Functions, seed data, database tests |
| `design/` | Canvas generator and brand marks |
| `docs/` | Specs and plans |

The tooling is pnpm workspaces + Turborepo. One root command (`pnpm dev`) starts the web and the app; `supabase start` runs the backend.

### 3.2 Principles

1. **The database enforces product rules.** Slot limits, privacy, ownership and trusted-only counts live in Postgres (constraints, row-level security, SQL functions), so a modified app or a script can't bypass them.
2. **Multi-step writes are one transaction.** Adding, swapping, promoting and deleting picks run as single SQL functions.
3. **Shared logic lives in `packages/core`.** The app and web never re-implement grouping or filtering differently.
4. **The canvas is the visual source of truth.** Screens match their artboards and the tokens come from the generator's values.

## 4. Data model

All tables use UUID primary keys and `created_at`/`updated_at` timestamps. Row-level security is on for every table.

| Table | Key columns | Rules |
|---|---|---|
| `profiles` | `id` (= auth user), `username` (unique, case-insensitive), `display_name`, `avatar_path`, `bio` (≤100), `home_place_text`, `home_location` (geography point), `visibility` (`public`/`private`), `trust_level` (`new`/`trusted`/`flagged`), `is_business_affiliated` + `affiliation_note` | private hides name and profile link on Discover/map and Nearby |
| `places` | `source` (`fsq`/`custom`), `source_id`, `name`, `area`, `city`, `region`, `country`, `location` (geography), `category_ids`, `created_by` (custom only), `merged_into_id` | unique (`source`, `source_id`); GiST index on `location`; trigram index on `name` |
| `dishes` | `place_id`, `name` (display), `name_key` (normalised), `merged_into_id` | unique (`place_id`, `name_key`) among unmerged dishes; trigram index on `name_key` |
| `picks` | `user_id`, `dish_id`, `tier` (`final`/`honorable`), `slot` (1–5, final only), `note` (≤280), `photo_path`, `original_dish_name` | unique (`user_id`, `dish_id`); unique (`user_id`, `slot`) where tier = final; a check makes slot required for final and null for honorable |
| `tags` | `kind` (`food_type`/`dietary`/`personal`), `name`, `slug`, `owner_id` (personal only), `is_featured` | food_type/dietary are global and admin-managed; personal tags are visible only to their owner |
| `pick_tags` | `pick_id`, `tag_id` | personal tags only on the owner's picks |
| `follows` | `follower_id`, `followee_id`, `status` (`active`/`requested`) | private accounts get `requested` until approved |
| `saves` | `user_id`, `dish_id` | "save to try" |
| `blocks` | `blocker_id`, `blocked_id` | blocked users never see each other |
| `shared_lists` | `owner_id`, `slug` (unique), `title`, `note`, `filter` (JSON: `scope` = `final_five`/`everything`/`custom`, `cities[]`, `food_type_tag_ids[]`, `dietary_tag_ids[]`, `personal_tag_ids[]`, `tiers[]`), `is_active` | evaluated live on every view; `filter` is validated by a shared schema in `packages/core` |
| `activities` | `actor_id`, `type` (`added_final`, `added_honorable`, `dethroned`, `promoted`, `followed`, `saved_pick`, `saved_from_list`), `pick_id`, `other_pick_id`, `list_id`, `target_user_id` | feeds the Following feed and notifications; respects privacy and blocks |
| `notifications` | `user_id`, `activity_id`, `read_at` | per-recipient inbox |
| `push_tokens` | `user_id`, `expo_token`, `platform` | |
| `device_attestations` | `user_id`, `platform`, `result`, `checked_at` | feeds trust |
| `reports` | `reporter_id`, `target_type` (`pick`/`profile`/`list`/`place`), `target_id`, `reason`, `status` | |

**Derived data:**

- `dish_stats` (materialised, refreshed on a schedule and after writes in batches): `final_count`, `honorable_count`, `list_count`. It counts **only picks from `trusted` accounts**.
- `place_stats`: the same at place level.

**Trust levels:**

- New accounts start `new`.
- They become `trusted` when all of these hold: account age ≥ 3 days, a profile photo or bio, at least 2 picks at 2 different places, attestation passed (on mobile), and not flagged.
- `flagged` is set by reports or pattern checks. Flagged accounts are excluded from counts and can be asked for step-up phone verification.
- A brand-new account's picks still show on its own profile, in its shared lists and in its followers' feeds. They just don't move counts, Nearby or trending.

## 5. Key flows

### 5.1 Sign-up (6 steps, matches the canvas)

1. Email.
2. Email code.
3. Name.
4. Username, with a live availability check.
5. Home city, chosen from a world cities list (GeoNames, cities over 15,000 people, CC BY 4.0) or from the phone's current location.
6. Photo (optional).

Apple and Google sign-in skip steps 1–2 and land on Name. Their buttons stay hidden until the developer accounts exist (Phase 8); until then sign-up is email code only. After step 6 comes the loading screen ("There can only be five."), then the first landing screen ("Your Final Meal has begun."); until adding dishes exists (Phase 3), the loading screen lands on the You tab instead. On mobile, the attestation check runs silently after sign-in.

### 5.2 Add a dish (one screen)

1. **Restaurant search.** Final Meal is a post-meal diary: people often log a dish after they've left or after a trip, so nothing uses their current location.
   - `search_places(query, city point)` queries our `places` table with trigram matching on the name, ranked near a chosen city. The city defaults to the home city and can be switched in the search.
   - "Can't find it? Add it" creates a custom place: a name, a street address (or "No fixed address" for food trucks and pop-ups) and a city. No location permission is used.
   - Custom places must be public businesses anyone can visit, never a home, because Final Meal is about restaurant discovery. The app asks people to confirm this.
   - Custom places' addresses are public, and they appear on the map (addresses get map positions in Phase 5). Who added a spot stays private.
2. **Dish field.** As you type, `suggest_dishes(place_id, text)` returns existing dishes at that place, ranked by similarity and pick count ("Tonkotsu Ramen · 14 picks here"). Choosing a suggestion links to it. Typing a new name creates a dish, and its `name_key` normalisation (lower case, accents removed, whitespace and punctuation collapsed, simple plural folding) prevents near-duplicates. If an unchosen name is a close fuzzy match (similarity ≥ 0.85) to an existing dish at the same place, it's linked and the person's wording is kept in `original_dish_name`.
3. **Final Meal or Honorable.** Choosing Final Meal with five already filled opens the swap screen, and `swap_final(new, replaced_slot)` moves the replaced pick to Honorable and records `dethroned`, all in one transaction.
4. **Optional parts:** photo (uploaded straight to storage, resized on read), note, and tags (expanding inline; "More" searches the full food-type and dietary lists; personal tags can be created inline).
5. `add_pick(...)` validates and writes everything in one transaction and returns the pick.

### 5.3 Share

- The share screen offers your five, everything, by city, by food type, by tag, a custom mix, and "See all", which opens **Your lists**.
- Creating a share makes a `shared_lists` row with a readable slug (`josies-vancouver`) and returns `https://<link-domain>/l/<slug>`.
- **On the web,** `/l/[slug]` renders server-side: the list view grouped by restaurant, a map view, Open Graph title and description, a generated preview image, and sign-up prompts. Saving or following from the web opens the sign-up sheet.
- **In the app,** iOS Universal Links and Android App Links (`apple-app-site-association` and `assetlinks.json`, served by Next.js) open the same list in the app when it's installed.
- Lists are live because the filter is evaluated on every view. Removing a pick or making the account private updates the list.

### 5.4 Feed, Discover, profile

- **Following feed:** activities from people you follow (active follows only), newest first, paginated.
- **Nearby feed:** recent picks from trusted public accounts within 25 km of your home location, ranked by recency and dish counts.
- **Discover:** map pins come from a bounding-box query (`picks_in_view`) that returns places with their best tier (a skull pin if any Final Meal, otherwise a bone dot). Private members' picks appear without a name or profile link. Search covers dishes, places, people and active shared lists. Filters cover pick type, distance, food type and dietary.
- **Profile:** Final Meal / Honorable / Map tabs come first, with a slim filter row under them (chips for cities, food types and tags) and "Share these" when a filter is active. The Final Meal tab lists the five individually; Honorable and the map group by restaurant.

### 5.5 Privacy

Decided by Josie on 2026-10-27.

- **Everyone starts Public.** Private is a setting.
- **Private accounts:**
  - Their name, @username and photo stay visible everywhere (search, followers lists, shared links), and anyone can open their profile.
  - The profile shows only the header (photo, name, @username, follower counts) plus "This account is private". Their picks, lists, bio details and **home city** are visible only to followers they approve.
  - Follows of a private account need approval.
  - Their picks still count on Discover and in counts (if trusted), but those pins show without their name or a profile link.
  - Lists they share by link show their name to anyone with the link.
- **Home city:** never shown for private accounts (except to approved followers). Public members can hide it with "Show my home city".
- **Blocks hide everything both ways.**
- **Timing:** the setting is stored from Phase 2; the read rules are enforced in Phase 7.

### 5.6 Errors and offline

- Every SQL function raises a named error code (`final_full`, `duplicate_pick`, `username_taken`, `place_not_found`, …). `packages/api` maps these to friendly copy that matches the canvas tone.
- The app caches the last loaded feed, profile and list for offline viewing. Writes need a connection and show a retry.
- Crash and error reporting goes through Sentry (free tier) for app and web.

## 6. Places pipeline

- **Source:** Foursquare Open Source Places through Foursquare's Places portal (registration and token required) or the Hugging Face mirror.
- **Import:** a script filters to food and drink categories, maps the fields (name, area/locality, region, country, coordinates, category IDs), and upserts by (`source`, `source_id`). It runs monthly in the cloud.
- **Locally:** a regional extract (Metro Vancouver) keeps the database small.
- **Attribution:** Foursquare's NOTICE text appears on the About screen and the web footer.
- **Custom places** stay `source = custom`. A later admin tool can merge them into Foursquare places via `merged_into_id`.

## 7. Maps

- MapLibre (`@maplibre/maplibre-react-native` in the app, `maplibre-gl` on the web) with a dark style tuned to the canvas palette.
- Tiles come from OpenFreeMap during development and the MVP; self-hosted Protomaps on object storage is the fallback if usage or terms require it.
- Pins are custom markers: a skull for Final Meal, a bone dot for Honorable, and a ring for the selected state.

## 8. Local development (Docker)

- **Prerequisites on Josie's Mac:** Docker Desktop (installed; must be running), Node (installed), Xcode + iOS Simulator with Expo Go installed in it (installed), pnpm (Claude installs it). - **Locally,** sign-in uses email codes only. Apple and Google sign-in, push notifications and attestation are switched on once the developer accounts exist. Until then a dev flag treats attestation as passed.
- **Environment files:** `.env.example` is committed; real `.env` files never are.

## 10. Testing

Tests are written before the code they cover.

- **Database:** pgTAP tests for slot limits, swaps, privacy, blocks, row-level security, trusted-only stats, and list-filter evaluation.
- **`packages/core`:** Vitest unit tests for name normalisation, restaurant grouping and filter schemas.
- **`packages/api`:** integration tests against the local Supabase.
- **Apps:** component tests (React Native Testing Library, React Testing Library); end-to-end flows with Maestro (mobile) and Playwright (web) for sign-up, add dish + swap, share + open on web.
- **CI:** GitHub Actions runs lint, type checks and tests on every push.
